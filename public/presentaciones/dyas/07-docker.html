1. El problema de los entornos

Una aplicación depende del intérprete, de las librerías y del sistema operativo donde se ejecuta, no solo de su código.

Cuando se despliega solo el código fuente, cada máquina lo ejecuta con lo que tenga instalado: otra versión de Python, otras versiones de las librerías, otras variables de entorno. El resultado es el conocido «en mi máquina funciona». Docker propone empaquetar la aplicación junto con su entorno en una imagen y mover esa imagen entre ambientes.

El mismo commit en dos máquinas

Ejemplo ilustrativo: las versiones del servidor son hipotéticas.

Qué viaja exactamente. Entre ambientes se mueve la imagen ya construida, identificada por su digest (sha256:…). Si cada ambiente reconstruye desde el Dockerfile, puede obtener otra imagen: en el taller, FROM python:3-slim resolvió a Python 3.14 en octubre de 2026, y en otra fecha resolverá a otra versión. La imagen tampoco elimina todas las diferencias: comparte el kernel del anfitrión y está construida para una arquitectura de CPU (amd64, arm64).

2. Máquinas virtuales y contenedores

Ambos aíslan aplicaciones, pero lo hacen en niveles distintos de la pila.

Pila de software
Comparación cualitativa (los valores dependen de la aplicación y del equipo)
AspectoMáquina virtualContenedor
Qué se virtualizaEl hardware: cada VM arranca su propio sistema operativo y su kernel.El sistema operativo: los procesos comparten el kernel del anfitrión y se aíslan con namespaces y cgroups.
ArranqueEl de un sistema operativo completo.El de un proceso.
Tamaño típicoGigabytes (imagen de disco con SO).Megabytes a cientos de megabytes (sin kernel).
AislamientoMás fuerte: la frontera es el hipervisor.Más débil: una falla del kernel afecta a todos los contenedores del anfitrión.
Unidad de distribuciónImagen de disco (VMDK, QCOW2, AMI…).Imagen OCI publicada en un registro (Docker Hub, GHCR…).
Sobre el aislamiento. Todos los contenedores de un anfitrión usan el mismo kernel, por lo que el aislamiento es menor que el de una VM. Por esa razón importan las prácticas de la sección 9 (usuario no root, imágenes mínimas) y por esa razón algunos proveedores de nube ejecutan los contenedores de clientes distintos dentro de VM separadas.

En Windows y macOS no existe un kernel Linux nativo. Docker Desktop ejecuta una VM Linux liviana (en Windows, sobre WSL2) y los contenedores corren dentro de ella. Por eso montar carpetas del anfitrión puede ser más lento y por eso se usan imágenes Linux también en esos sistemas.

3. Imágenes, capas y caché

Cada instrucción que modifica el sistema de archivos produce una capa. Si una capa cambia, todas las siguientes se vuelven a construir.

Una imagen es una pila de capas de solo lectura más un archivo de configuración (variables de entorno, puerto expuesto, comando de inicio). Al construir, BuildKit compara cada instrucción y los archivos que usa con la construcción anterior. Para COPY compara el contenido de los archivos copiados: si alguno cambió, esa capa y todas las posteriores se invalidan. Por eso el orden de las instrucciones determina cuánto se reconstruye.

5. Ciclo de vida de un contenedor

  
Una imagen es una plantilla de solo lectura. Un contenedor es una instancia de esa imagen con una capa escribible propia.

  

    

      Estados y comandos
      
    

    
    

      
      
      
      
      
      
      
      
    

    

    

      
Capa escribible del contenedor

      
Volumen datos montado en /data

    

    
Comando base: docker run -d --name cache -v datos:/data redis:8.2 redis-server --appendonly yes. Los mensajes de error están abreviados.

  

  

    
Capa escribible
Todo lo que el proceso escribe fuera de un volumen queda en la capa escribible. Sobrevive a stop y start, pero desaparece con docker rm. Con --rm el contenedor se elimina al detenerse, lo que es útil para tareas de una sola ejecución.

    
Volumen
Un volumen tiene un ciclo de vida independiente del contenedor. Los datos de Redis en /data siguen disponibles al crear un contenedor nuevo con el mismo volumen. El taller usa un bind mount (./data:/data), que es una carpeta del anfitrión; un volumen con nombre lo administra Docker.

  


  
Publicación de puertos

  
El contenedor tiene su propia interfaz de red. -p 4000:80 significa «puerto 4000 del anfitrión hacia el puerto 80 del contenedor»: el primer número es el del anfitrión.

6. Docker Compose

  
Compose describe en un archivo YAML varios servicios, sus redes y sus volúmenes, y los levanta con un solo comando.

  

    


# docker-compose.yaml (versión original)
services:
  web:
    build: .
    ports:
      - "4000:80"
  redis:
    image: redis
    ports:
      - "6379:6379"
    volumes:
      - "./data:/data"
    command: redis-server --appendonly yes

    

    

      
Qué crea docker compose up

      
    
        
  • Una red propia del proyecto (friendlyhello_default) a la que se conectan todos los servicios.
    • 
        
  • Un DNS interno en esa red: cada servicio se resuelve por su nombre. Por eso app.py usa Redis(host="redis") y no una IP.
    • 
        
  • Los contenedores friendlyhello-web-1 y friendlyhello-redis-1.
    • 
        
  • Publicar 6379 no es necesario para que web llegue a Redis; solo sirve para conectarse desde el anfitrión y expone la base de datos fuera de la red.
    • 
      

    

  


  

    

      GET / en http://localhost:4000
      

        
        
        
        
      

    

    
    

  


  

    Contenedor web sin Redis VERIFICADO
    
Al ejecutar solo el contenedor de la aplicación, sin Redis, cada petición HTTP tardó entre 92 y 96 segundos. requirements.txt declara Redis sin versión y pip instaló redis-py 8.1.0, que por defecto reintenta las operaciones fallidas 10 veces con espera exponencial. Cada intento incluye una resolución DNS fallida del nombre redis, que en esa máquina llegó a tardar unos 14 s. socket_connect_timeout=2 no acota ese tiempo porque limita la conexión TCP, no la resolución del nombre.

    
Con Redis(..., retry=Retry(NoBackoff(), 0)) la petición bajó a unos 7 s. En una repetición posterior en la misma máquina, la resolución fallida tardó entre 4 y 15 s según el intento, de modo que una petición sin reintentos tarda lo que tarde el DNS.

    
Conclusión práctica: fijar las versiones de las dependencias y configurar de forma deliberada los tiempos de espera y los reintentos de cada cliente de red.

  

  

    


# app.py: sin reintentos implícitos
from redis import Redis, RedisError
from redis.backoff import NoBackoff
from redis.retry import Retry

redis = Redis(host="redis", db=0,
              socket_connect_timeout=2, socket_timeout=2,
              retry=Retry(NoBackoff(), 0))

# requirements.txt: versiones fijas
Flask==3.1.3
redis==8.1.0

    

    


# depends_on solo ordena el arranque.
# Para esperar a que Redis responda: healthcheck.
services:
  web:
    build: .
    ports:
      - "4000:80"
    depends_on:
      redis:
        condition: service_healthy
  redis:
    image: redis:8.2
    command: redis-server --appendonly yes
    volumes:
      - "./data:/data"
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

    

  

  
Los dos fragmentos se probaron con Docker Engine 28.5.1 y Compose v2.40.3: docker compose config sin errores, Redis pasó a healthy antes de iniciar web y el contador respondió. depends_on sin condición solo garantiza que el contenedor de Redis se haya iniciado, no que acepte conexiones.







  
7. Escalamiento y balanceo de carga con Traefik

  
Varias réplicas del servicio web detrás de un proxy inverso que reparte las peticiones.

  
Con docker compose up -d --scale web=5 Compose crea cinco contenedores del servicio web. Ya no se puede publicar 4000:80 en cada uno (el puerto del anfitrión es único), así que Traefik recibe las peticiones en el puerto 4000, descubre las réplicas leyendo las etiquetas de los contenedores a través del socket de Docker y las reparte en round-robin. Como el contador vive en Redis, el número de visitas es global aunque responda una réplica distinta cada vez.

Los hostnames son de ejemplo: cada réplica responde con el identificador corto de su contenedor.

  

  

    


# fragmento del docker-compose.yaml original
services:
  web:
    build: .
    labels:
    - "traefik.enable=true"
    - "traefik.http.routers.web.rule=Host(`localhost`)"
    - "traefik.http.routers.web.entrypoints=web"
    - "traefik.http.services.web.loadbalancer.server.port=80"
  traefik:
    image: traefik:v3.7      # antes: v2.3
    command:
    - "--api.insecure=true"
    - "--providers.docker=true"
    - "--providers.docker.exposedByDefault=false"
    - "--entrypoints.web.address=:4000"
    ports:
    - "4000:4000"
    - "8080:8080"   # dashboard
    volumes:
    - "/var/run/docker.sock:/var/run/docker.sock"

    

    

      

        
Prueba del taller VERIFICADO

        
    
          
  • Docker Engine 28.5.1 y Compose v2.40.3.
    • 
          
  • traefik:v2.3 funcionó; su log registró Provider connection established with docker 28.5.1 (API 1.51).
    • 
          
  • Los hostnames rotaron en round-robin entre las cinco réplicas.
    • 
          
  • traefik:v3 (3.7.13) funcionó con las mismas etiquetas y los mismos parámetros; solo cambió la etiqueta de la imagen.
    • 
          
  • curl http://127.0.0.1:4000 devolvió 404 page not found, porque la regla es Host(`localhost`).
    • 
        

      

    

  

  

    Riesgo con versiones nuevas de Docker INFERIDO
    
Docker Engine 29 elevó la versión mínima de API aceptada a 1.44. Imágenes muy antiguas de Traefik, que negocian una API anterior, podrían no conectarse al proveedor Docker en ese motor. No se probó con Engine 29; la recomendación es usar traefik:v3.x con una versión menor fija.

  

  

    Alcance de la demostración. Cinco réplicas en un solo anfitrión reparten carga, pero no dan alta disponibilidad: si cae la máquina, caen todas, y Redis sigue siendo una única instancia. La alta disponibilidad real requiere varios nodos y un orquestador (Docker Swarm o Kubernetes). Además, montar /var/run/docker.sock le da a Traefik control total sobre Docker, y --api.insecure=true publica el dashboard sin autenticación: ambas cosas son aceptables en un taller local, no en producción.

Lista de verificación para revisar un Dockerfile. Cada punto incluye la evidencia observada en el taller o la razón técnica.

  

    

      Revisión del Dockerfile
      

        
        
      

    

    

      

      

        

          
          

        

      

    

  

  
Versión revisada del Dockerfile de friendlyhello

  

    


# syntax=docker/dockerfile:1
FROM python:3.14-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN useradd --system --no-create-home app
USER app
EXPOSE 8000
ENV NAME=World
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --start-interval=2s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health', timeout=2)"
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "--workers", "2", "app:app"]

# requirements.txt
Flask==3.1.3
redis==8.1.0
gunicorn==26.2.0

    

    

      
    
        
  • Probado con Docker Engine 28.5.1: docker build --check sin advertencias, el contenedor corre como uid=999(app), el estado pasa a healthy, el contador responde y docker stop tardó alrededor de 1 s. VERIFICADO
    • 
        
  • El HEALTHCHECK consulta /health, un endpoint que no usa Redis. Si consultara /, sin Redis cada petición tarda varios segundos (la búsqueda DNS de redis falla) y el contenedor quedaría unhealthy. Con --start-interval=2s el contenedor pasa a healthy en pocos segundos, lo que importa porque Traefik solo envía tráfico a réplicas healthy. VERIFICADO
    • 
        
  • El puerto pasa de 80 a 8000 porque el proceso ya no es root. Docker permite a procesos sin privilegios abrir puertos bajos dentro del contenedor, pero otros entornos (Kubernetes con políticas restrictivas, Podman sin root) no siempre. Hay que ajustar -p 4000:8000 y la etiqueta loadbalancer.server.port=8000.
    • 
        
  • Fijar python:3.14-slim fija la versión menor; para reproducibilidad total se fija el digest: python:3.14-slim@sha256:…, y se actualiza de forma deliberada (por ejemplo, con Dependabot o Renovate).

10. Escaneo de vulnerabilidades con Trivy

  
Relación con DevSecOps. Trivy analiza los paquetes del sistema operativo de la imagen y las dependencias de la aplicación, y los compara con bases de datos de vulnerabilidades conocidas (CVE).

  

    

      trivy image --severity CRITICAL,HIGH registraduria
      
    

    
Imagen del proyecto registraduria (Spring Boot 2.7.18) construida con el Dockerfile de la sección 4.

    

    

  

  

    

      
Resultado del escaneo VERIFICADO

      
    
        
  • Trivy 0.74.0, filtro CRITICAL,HIGH.
    • 
        
  • Paquetes del sistema operativo (Ubuntu 26.04 de eclipse-temurin:21-jre): 0 hallazgos.
    • 
        
  • Dependencias Java del .jar: 48 hallazgos, 8 CRITICAL y 40 HIGH, que corresponden a 47 CVE distintos (CVE-2023-6378 aparece en logback-core y en logback-classic).
    • 
        
  • 46 de los 47 CVE tienen versión corregida. El restante, CVE-2026-41849 en spring-expression 5.3.31, no tiene corrección publicada para la rama 5.3.
    • 
      

    

    

      
Interpretación

      
La imagen base estaba limpia; el riesgo provino de las dependencias del framework. Spring Boot 2.7 ya no tiene soporte de código abierto. La corrección consiste en migrar a una versión soportada de Spring Boot (3.x o posterior); cambiar la imagen base no resuelve estos hallazgos.

      
Un escaneo refleja la base de datos del día en que se ejecuta. La misma imagen, escaneada un mes después, puede tener más hallazgos sin que nadie la haya modificado; por eso el escaneo se repite en cada pipeline y también de forma periódica.

    

  







  
11. Docker en el pipeline de CI

  
Conexión con la integración continua y con la Entrega 3 del proyecto, que exige Docker y el escaneo de la imagen (por ejemplo, con Trivy); Kubernetes es una bonificación.

  
El workflow del repositorio DAYS-Integracion_continua compila y prueba en un job build. Se agrega un job imagen que depende de él (needs: build): construye la imagen, la escanea con Trivy y, solo si el escaneo pasa, la publica en GitHub Container Registry (GHCR). La etiqueta es el SHA del commit, de modo que cada imagen se puede rastrear hasta el código que la produjo.

  

    

      Ejecución del workflow en un push a main
      

        
        
        
      

    

    

    

  


name: CI

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-java@v6
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
      - name: Compilar y probar
        run: mvn -B -ntp verify
      - name: Publicar reportes
        if: always()
        uses: actions/upload-artifact@v7
        with:
          name: reportes-pruebas
          path: target/surefire-reports/

  imagen:
    needs: build
    if: github.event_name == 'push'
    runs-on: ubuntu-24.04
    permissions:
      contents: read
      packages: write
    env:
      TRIVY_VERSION: 0.75.0
    steps:
      - uses: actions/checkout@v7

      - name: Nombre de la imagen (GHCR exige minúsculas)
        run: echo "IMAGE=ghcr.io/${GITHUB_REPOSITORY,,}" >> "$GITHUB_ENV"

      - name: Construir imagen
        run: docker build -t "$IMAGE:$GITHUB_SHA" .

      - name: Escanear con Trivy
        run: |
          docker run --rm \
            -v /var/run/docker.sock:/var/run/docker.sock \
            "aquasec/trivy:$TRIVY_VERSION" image \
            --severity CRITICAL,HIGH --ignore-unfixed --exit-code 1 \
            "$IMAGE:$GITHUB_SHA"

      - name: Publicar en GHCR
        run: |
          echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io -u "${{ github.actor }}" --password-stdin
          docker push "$IMAGE:$GITHUB_SHA"

  

    

      
Decisiones del job imagen

      
    
        
  • Usa comandos docker directamente y la imagen oficial de Trivy con versión fija (por ejemplo, 0.75.0), en lugar de acciones de terceros.
    • 
        
  • ${GITHUB_REPOSITORY,,} convierte el nombre a minúsculas: DAYS-Integracion_continua tiene mayúsculas y GHCR las rechaza.
    • 
        
  • packages: write solo en este job; el resto del workflow queda con contents: read.
    • 
        
  • --exit-code 1 hace fallar el job si hay hallazgos CRITICAL o HIGH con corrección disponible; con las dependencias actuales de registraduria el job falla y la imagen no se publica.
    • 
      

    

    

      
Requisitos de versión de las acciones

      
    
        
  • GitHub retiró Node 20 de los runners el 23 de septiembre de 2026. Las acciones deben estar en versiones mayores basadas en Node 24: checkout@v7, setup-java@v6 y upload-artifact@v7 (últimas versiones publicadas: 7.0.1, 6.0.1 y 7.0.1).
    • 
        
  • El workflow completo se revisó con actionlint sin errores.
    • 
        
  • El paso siguiente de la Entrega 3 es desplegar en Kubernetes la imagen publicada, referenciándola por su etiqueta de SHA o por su digest.
