REST no es «una API con JSON sobre HTTP»

REST es un conjunto de seis restricciones que Roy Fielding derivó en el año 2000 para explicar por qué la Web escaló. Cada restricción compra una propiedad y cuesta algo. Diseñar bien exige saber cuál se está aceptando y cuál se está sacrificando.

1. Origen y tesis

REST se formuló como una explicación, no como una receta.

Fielding trabajaba en la especificación de HTTP/1.1 y URI. Su tesis doctoral no propone un método para construir APIs: describe, mediante restricciones acumulativas, el estilo arquitectónico que hace que un sistema hipermedia distribuido a escala planetaria funcione con cachés intermedias, proxies desconocidos y clientes que evolucionan de forma independiente del servidor.

Esa diferencia importa: casi todo lo que la industria llama «API REST» es en realidad HTTP-RPC sobre recursos, y en la mayoría de los casos esa elección es correcta. Lo problemático no es apartarse de REST; es apartarse sin saberlo y luego sorprenderse porque no se obtienen las propiedades que REST prometía.

Las seis restricciones y qué se rompe si se omiten Fielding, 2000 — cap. 5

1 · Cliente–servidor

Separa la interfaz de usuario del almacenamiento. Ambos evolucionan por separado.

Sin ella: cada cambio de UI obliga a redesplegar el servidor.

2 · Sin estado (stateless)

Cada petición lleva todo lo necesario para ser entendida. El servidor no guarda contexto de sesión.

Sin ella: no hay balanceo trivial ni escalado horizontal; toda instancia debe conocer la sesión.

3 · Cacheable

Las respuestas se marcan explícitamente como cacheables o no.

Sin ella: se pierde la mayor fuente de rendimiento de la Web; toda lectura llega al origen.

4 · Interfaz uniforme

Recursos identificados por URI, manipulados por representaciones, mensajes autodescriptivos, hipermedia como motor del estado.

Sin ella: cada API es un protocolo nuevo y ninguna herramienta genérica sirve.

5 · Sistema en capas

El cliente no sabe si habla con el origen o con un intermediario.

Sin ella: no se pueden insertar gateway, CDN, WAF ni balanceador sin cambiar clientes.

6 · Código bajo demanda (opcional)

El servidor puede enviar código ejecutable al cliente. Es la única restricción opcional.

Sin ella: no se pierde nada esencial; casi ninguna API la usa.

2. Modelo de madurez de Richardson

Un instrumento de diagnóstico, no una escalera que haya que subir hasta el final.


      

        

        

        

      

    

  


  

    Postura defendible. El nivel 2 es el punto de equilibrio para la enorme mayoría de las APIs empresariales: se obtiene caché, semántica uniforme, códigos de estado interpretables por intermediarios y herramientas estándar. El nivel 3 (HATEOAS) solo se paga cuando existen clientes que no se controlan y deben adaptarse a cambios de flujo sin redesplegarse —por ejemplo, una API pública de larga vida—. Exigir HATEOAS en una API interna consumida por un único front-end es ceremonia sin beneficio, y conviene decirlo con esa franqueza en clase.
  






  
3. Semántica de los métodos: seguridad e idempotencia

  
Esta tabla es lo que hace que reintentar sea seguro. Es la parte de REST con consecuencias operativas directas.

  

    Seguro: no modifica estado observable. Idempotente: ejecutarlo N veces deja el mismo estado que ejecutarlo una vez.
    
MétodoSeguroIdempotenteCacheableConsecuencia práctica

    
      
GETSíSíSíCualquier intermediario puede reintentarlo y cachearlo. Nunca use GET para operaciones con efecto.

      
HEADSíSíSíVerificación de existencia y metadatos sin transferir el cuerpo.

      
PUTNoSíNoReemplazo completo. Un reintento tras timeout es seguro.

      
DELETENoSíNoIdempotente en estado: el segundo intento devuelve 404 o 204, pero el recurso sigue borrado.

      
POSTNoNoSolo con Cache-Control explícitoReintentar puede duplicar. Requiere clave de idempotencia si la red no es confiable.

      
PATCHNoNo*No*Puede diseñarse idempotente (JSON Merge Patch) o no serlo (operación «incrementar en 1»).

    
  


  
El caso que aparece en todo sistema de pagos

  

    


# El cliente envía un pago y la respuesta se pierde
# por timeout de red. ¿Reintentar?
POST /v1/pagos
Idempotency-Key: 9c1f4a2e-7b30-4d51-9e08-4f2ab7c61d55
Content-Type: application/json

{ "cuentaOrigen": "0011-4482",
  "monto": 189900,
  "moneda": "COP" }

    

    

      
El servidor almacena la clave junto con la respuesta producida. Si llega una segunda petición con la misma clave:

      
    
        
  • Devuelve la misma respuesta original, sin ejecutar el pago de nuevo.
    • 
        
  • Si el cuerpo difiere para la misma clave, responde 422: es un error del cliente, no un pago distinto.
    • 
        
  • La clave expira (24 h es habitual) y la genera el cliente, no el servidor.
    • 
      

      
Sin esto, la combinación de reintentos automáticos del cliente móvil y latencia del backend produce cobros duplicados. No es un detalle de implementación: es una decisión de contrato que debe estar en el diseño.

    

  






  
4. Diseño de recursos: errores frecuentes

  
Un recurso es un sustantivo con identidad estable, no una llamada a procedimiento disfrazada.

  

    
Diseño frecuenteAlternativaRazón

    
      
GET /obtenerCliente?id=44GET /clientes/44El verbo está en el método HTTP. La URI identifica, no ordena.

      
POST /clientes/44/borrarDELETE /clientes/44POST bloquea la idempotencia y confunde a los intermediarios.

      
GET /clientes/44/pedidos/todosGET /clientes/44/pedidos?estado=activoFiltros y paginación van en query string; la jerarquía en la ruta.

      
200 OK con {"error":"no existe"}404 + application/problem+jsonUn intermediario no puede interpretar un error escondido en un 200. RFC 9457 estandariza el cuerpo de error.

      
POST /transferencias/ejecutarPOST /transferenciasLa transferencia es un recurso con identidad, estado y consulta posterior; no una acción efímera.

      
GET /pedidos que devuelve 40 000 filasPaginación por cursor + LinkLas colecciones sin límite superior son un incidente esperando ocurrir.

    
  


  

    Excepción legítima. Algunas operaciones no son recursos por más que se fuerce el modelo: POST /cuentas/44/cierre, POST /busquedas con un cuerpo de consulta complejo. Modelar la acción como un recurso de proceso (con su propio identificador y estado consultable) suele ser mejor que inventar un sustantivo artificial. Diseñar bien es reconocer cuándo la restricción deja de pagar.
  






  
5. Caché condicional: la restricción con mayor retorno

  
Es la parte de REST que más rendimiento entrega y la que más se ignora en APIs internas.

  

    


--- Primera petición ---
GET /productos/8812
200 OK
ETag: "v41-9ab3"
Cache-Control: private, max-age=60

{ "nombre": "Teclado mecánico", "precio": 289900 }

--- 3 minutos después ---
GET /productos/8812
If-None-Match: "v41-9ab3"
304 Not Modified   ← sin cuerpo

    

    

      
Lo que compra

      
    
        
  • Un 304 transfiere encabezados, no el cuerpo: en catálogos grandes reduce el tráfico en más de un orden de magnitud.
    • 
        
  • El mismo ETag habilita concurrencia optimista: PUT con If-Match devuelve 412 si otro cliente modificó el recurso. Es control de concurrencia sin bloqueo en base de datos.
    • 
        
  • Los intermediarios (CDN, gateway) participan sin que el servicio los conozca — esa es la restricción de sistema en capas produciendo valor.
    • 
      

      
Lo que cuesta

      
    
        
  • Calcular el ETag requiere versión o hash estables del recurso.
    • 
        
  • Toda política de frescura es una decisión de negocio: ¿cuántos segundos de desactualización tolera el usuario? Esa pregunta se acuerda con el dueño de producto, no se decide en el código.
    • 
      

    

  






  
6. REST frente a las alternativas

  
Ninguna es superior. Cada una optimiza una variable distinta y empeora otra.

  

    
CriterioREST / HTTP+JSONgRPCGraphQLMensajería asíncrona

    
      
Encaja cuandoAPI pública o entre equipos; lecturas cacheablesComunicación interna de alto volumen y baja latenciaMuchos clientes con necesidades de datos distintasDesacople temporal; el emisor no espera respuesta

      
ContratoOpenAPI (frecuentemente escrito después del código)Protobuf, obligatorio y verificado en compilaciónEsquema tipado, introspectableEsquema de evento (Avro/JSON Schema) en un registro

      
RendimientoTexto; sobrecarga de HTTP por llamadaBinario + HTTP/2 multiplexado: menor latencia y payloadUna ida y vuelta para datos que REST pediría en variasAlto throughput; la latencia deja de ser observable por el usuario

      
CachéNativa en toda la infraestructura webDebe implementarse a manoDifícil: POST único y consultas variablesNo aplica

      
Costo ocultoN+1 peticiones y sobre-transferencia de datosDepuración menos accesible; soporte de navegador limitadoConsultas costosas del cliente pueden tumbar el backend; exige límites de profundidad y complejidadConsistencia eventual, orden y duplicados a cargo del consumidor

    
  

  

    Regla de decisión aplicable. Contrato hacia afuera o hacia otros equipos, con lecturas repetidas: REST. Tráfico interno intensivo entre servicios propios: gRPC. Un front-end que sufre para componer datos de muchos recursos: GraphQL o un Backend for Frontend. Trabajo que no necesita respuesta inmediata: mensajería. La mayoría de los sistemas empresariales de 2026 usan tres de las cuatro a la vez, y eso es correcto: el estilo se elige por interacción, no por sistema.
  






  
7. Marco de decisión

  

    

      
REST es la elección correcta cuando

      
    
        
  • El consumidor es desconocido, externo o numeroso: HTTP es el único denominador común universal.
    • 
        
  • Predominan las lecturas y la caché entrega beneficio medible.
    • 
        
  • Se necesita atravesar infraestructura corporativa (proxies, WAF, gateway) sin negociaciones especiales.
    • 
        
  • El modelo de interacción es realmente sobre recursos con ciclo de vida.
    • 
        
  • Importa la accesibilidad de la depuración: curl, navegador y logs legibles.
    • 
      

    

    

      
Considere otra opción cuando

      
    
        
  • Se necesita streaming bidireccional o notificación push: gRPC streaming, WebSocket o SSE.
    • 
        
  • La latencia por llamada domina el presupuesto de rendimiento en tráfico interno intensivo.
    • 
        
  • El cliente requiere composiciones muy variables que producen N+1 peticiones.
    • 
        
  • La operación es de larga duración: modele un recurso de proceso con 202 Accepted y consulta de estado, o pase a mensajería.
    • 
        
  • El dominio es intrínsecamente de eventos, no de recursos (telemetría IoT, flujos de auditoría).
    •
