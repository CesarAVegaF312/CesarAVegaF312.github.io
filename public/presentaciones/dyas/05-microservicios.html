Microservicios: comprar autonomía con complejidad distribuida

Un microservicio no es «un servicio pequeño». Es una unidad de despliegue con dueño único, datos propios y libertad de cambio. Todo lo demás del estilo —sagas, outbox, gateway, observabilidad— es la factura que se paga por esa libertad.

1. La definición útil (y la que induce a error)

La granularidad no es el criterio. La autonomía sí.

Definición que produce malas arquitecturas

«Servicios pequeños que hacen una sola cosa y se comunican por API.» Aplicada literalmente, lleva a decenas de servicios anémicos que no pueden atender una sola petición sin llamarse entre sí en cadena. El resultado es un monolito distribuido: la complejidad del monolito más la latencia y los modos de falla de la red.

Definición que resiste el escrutinio

Un servicio que se despliega, escala, falla y evoluciona de forma independiente, porque es dueño exclusivo de sus datos y su contrato está versionado. Si dos servicios deben desplegarse juntos para no romperse, no son dos microservicios: son un servicio con una llamada de red innecesaria en el medio.

Prueba práctica de autonomía. ¿Puede su equipo desplegar el servicio A un martes a las 3 p.m. sin avisar a ningún otro equipo, sin coordinar una migración de esquema ajena y sin que ninguna otra prueba de integración falle? Si la respuesta es no, tiene servicios distribuidos, no microservicios.

Los tres tipos de límite que definen un servicio

Límite de negocio

Un contexto delimitado del DDD: «Pagos» y «Pedidos» usan la palabra orden con significados distintos. Esa diferencia semántica es la costura natural.

Límite de datos

Un conjunto de entidades que cambian juntas y necesitan consistencia inmediata entre sí. Ese conjunto no se puede partir sin introducir sagas.

Límite organizacional

Un equipo que pueda mantenerlo de punta a punta. Ley de Conway: la arquitectura tenderá a copiar la estructura de comunicación de la empresa, la reconozca usted o no.

2. La aritmética que casi nadie hace antes de migrar

Cada llamada síncrona en la ruta crítica multiplica probabilidades de falla. Esta es la cuenta que convierte una decisión de moda en una decisión de ingeniería.

Disponibilidad compuesta en una cadena síncrona Atotal = An

Una petición del usuario atraviesa 4 servicios en cadena, cada uno con disponibilidad individual de 99,9%.

Lectura arquitectónica. Con seis servicios de 99,9% en cadena usted no tiene 99,9%: tiene 99,4%, es decir más de dos días de indisponibilidad al año. La respuesta no es exigir más nueves a cada equipo, sino sacar servicios de la ruta crítica: caché, valores por defecto, comunicación asíncrona y degradación funcional. Un servicio que responde con datos de hace 30 segundos casi siempre es mejor que uno que no responde.

3. El dato es el límite real

La mayoría de las migraciones fallidas partieron el código y dejaron la base de datos intacta.

Base compartida frente a datos privados

Lo que se pierde al partir la base de datos

Se pierde la transacción ACID que abarcaba varias tablas. Ese es el costo central del estilo, y no tiene solución gratuita: se sustituye por consistencia eventual y por protocolos explícitos de compensación. Cualquier presentación que muestre microservicios sin nombrar esta pérdida está incompleta.

Precisión conceptual. Es incorrecto decir que «los microservicios cumplen ACID». Cada servicio mantiene ACID dentro de su propia base; entre servicios rige BASE (Basically Available, Soft state, Eventually consistent). El teorema de CAP y el modelo BASE describen el régimen entre servicios; ACID describe el régimen interno. Confundirlos produce diseños que prometen atomicidad que el sistema no puede entregar.

Orquestación

  • Un coordinador explícito conoce el estado de la saga y decide el siguiente paso.
  • Ventaja: el flujo es legible, depurable y auditable en un solo lugar.
  • Costo: el orquestador acopla a los participantes y puede convertirse en el nuevo cuello de botella organizacional.
  • Usar cuando el proceso tiene reglas de negocio propias y debe ser auditado por un regulador.

Coreografía

  • Cada servicio reacciona a eventos y publica los suyos. No hay coordinador.
  • Ventaja: acoplamiento mínimo; agregar un participante no exige modificar a nadie.
  • Costo: nadie conoce el estado global. Sin trazabilidad distribuida, diagnosticar una saga trabada es forense.
  • Usar cuando los pasos son reacciones independientes y el orden no es una regla de negocio.

5. Outbox: el bug que aparece una vez cada diez mil pedidos

El problema de la doble escritura es el error más caro y menos visible del estilo.

El código que parece correcto

// Anti-patrón: dos sistemas, sin transacción común
@Transactional
public void confirmar(OrderId id) {
    Order order = repository.findById(id);
    order.confirm();
    repository.save(order);        // commit en PostgreSQL
    events.publish(new OrderConfirmed(id));  // envío a Kafka
}

Si el proceso muere entre el commit y el publish, el pedido queda confirmado y nadie lo despacha. Si el publish ocurre y el commit se revierte, se despacha un pedido que no existe. La anotación @Transactional no cubre al broker: son dos recursos distintos.

Outbox: una sola transacción, dos efectos

// El evento se escribe en la misma base, misma transacción
@Transactional
public void confirmar(OrderId id) {
    Order order = repository.findById(id);
    order.confirm();
    repository.save(order);
    outbox.save(OutboxMessage.from(new OrderConfirmed(id)));
}
// Un relay (Debezium o poller) lee la tabla outbox
// y publica en Kafka con garantía at-least-once.
  • La atomicidad se recupera porque ambos escritos van a la misma base.
  • La entrega es al menos una vez: los consumidores deben ser idempotentes.
  • Costo: latencia adicional del relay y una tabla más que operar y purgar.

6. Prerrequisitos organizacionales

Marque lo que su organización ya tiene. La lista no es de tecnologías deseables: es de condiciones sin las cuales el estilo produce más daño que beneficio.

Marque los elementos disponibles para obtener un veredicto.
Recomendación fundamentada. Para un sistema nuevo, empiece con un monolito modular: módulos con límites explícitos, sin dependencias cruzadas y con esquemas de datos separados dentro de la misma base. Cuando un módulo demuestre una razón concreta para independizarse —escala desigual, cadencia de cambio distinta, o un equipo dedicado— extráigalo. La extracción desde un monolito bien modularizado es un trabajo de semanas; encontrar los límites correctos desde cero, sin conocer el dominio, cuesta años de refactorización distribuida.

7. Marco de decisión y atributos de calidad

Adopte microservicios cuando

  • Distintas partes del sistema tienen perfiles de carga muy distintos y escalarlas juntas es caro.
  • Varios equipos se bloquean mutuamente en el mismo repositorio y en la misma ventana de despliegue.
  • Un subdominio cambia con una frecuencia radicalmente distinta al resto.
  • Se necesita aislar el radio de impacto de una falla en una capacidad crítica.
  • Existe una razón técnica genuina para heterogeneidad tecnológica (por ejemplo, un motor de inferencia en Python junto a un core transaccional en Java).

Evite microservicios cuando

  • El sistema es nuevo y el dominio todavía no está estabilizado.
  • Un solo equipo construye y opera todo el producto.
  • La consistencia inmediata entre entidades es un requisito de negocio no negociable.
  • No existe automatización de despliegue ni observabilidad distribuida.
  • El sistema es principalmente CRUD sobre un modelo de datos altamente relacionado.

La pregunta correcta no es si adoptar microservicios, sino qué parte del sistema tiene hoy una razón medible para independizarse.
