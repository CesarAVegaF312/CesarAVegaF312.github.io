Programación reactiva

1. ¿Por qué programación reactiva?

El modelo reactivo cambia lo que hace un hilo mientras espera una operación de entrada/salida (E/S).

En el modelo clásico de servidor (Servlet, Spring MVC) cada petición ocupa un hilo de principio a fin. Si la petición consulta una base de datos que tarda 300 ms, el hilo pasa esos 300 ms bloqueado: no usa CPU, pero ocupa memoria (su pila) y un cupo del pool. Cuando la carga está dominada por E/S, el límite deja de ser la CPU y pasa a ser el número de hilos disponibles.

En el modelo no bloqueante pocos hilos (en Netty, un event loop por núcleo) registran la operación de E/S, atienden otra tarea y retoman la petición cuando llega la respuesta. Ningún hilo queda esperando.

Hilo por petición y event loop con E/S lenta
CPU: preparar la petición hilo bloqueado esperando E/S CPU: responder operaciones de E/S en vuelo (sin hilo)

Modelo ilustrativo, no una medición. Cada petición = 0,5 u de CPU para preparar + 6 u de espera de E/S + 0,5 u de CPU para responder. Pool de 4 hilos frente a 1 event loop. Unidades de tiempo arbitrarias.

Límites del modelo. La programación reactiva no acelera un cálculo. Si el trabajo es intensivo en CPU, un event loop no tiene ventaja sobre un pool de hilos. La ventaja también desaparece si algún operador bloquea el event loop, por ejemplo una llamada JDBC dentro de un map: ese hilo deja de atender a todas las demás peticiones.

El contrato: Reactive Streams

Reactor y RxJava 2/3 implementan la especificación Reactive Streams (incorporada en Java 9 como java.util.concurrent.Flow). Son cuatro interfaces y una regla central: el suscriptor indica cuántos elementos puede recibir con request(n) y el publicador nunca envía más de lo pedido.

// org.reactivestreams
public interface Publisher<T> {
    void subscribe(Subscriber<? super T> s);
}
public interface Subscriber<T> {
    void onSubscribe(Subscription s);
    void onNext(T t);
    void onError(Throwable t);
    void onComplete();
}
public interface Subscription {
    void request(long n);   // demanda: "puedo recibir n más"
    void cancel();
}
public interface Processor<T, R> extends Subscriber<T>, Publisher<R> { }

Orden de las señales

onSubscribe → request(n) → onNext × (≤ n) → onComplete | onError

  • Como máximo una señal terminal: onComplete u onError. Después de ella no llega nada más.
  • Un error es una señal terminal: el flujo termina, a menos que un operador lo transforme (sección 6).
  • Mientras no haya subscribe(), nada se ejecuta: el código solo ensambla el pipeline.
Flux<String> f = Flux.range(1, 3)
    .map(i -> { System.out.println("map " + i); return "v" + i; });
// Hasta aquí no se imprime nada.
f.subscribe();   // map 1, map 2, map 3
f.subscribe();   // se repite: cada suscripción ejecuta de nuevo

    flatMap, concatMap y flatMapSequential. Los tres convierten cada elemento en un publicador interno. flatMap se suscribe a todos los internos de inmediato y emite según terminan, por lo que no garantiza el orden. concatMap procesa un interno a la vez y preserva el orden, pero suma las latencias. flatMapSequential (Reactor) o concatMapEager (RxJava) se suscriben a todos a la vez y reordenan la salida: concurrencia de flatMap con el orden de concatMap, a cambio de retener en memoria los resultados que llegan antes de tiempo.

3. Hilos con subscribeOn y publishOn

  
Un operador no crea hilos. Los Scheduler deciden en qué hilo corre cada tramo del pipeline. En RxJava el equivalente de publishOn se llama observeOn.

  

    

      
subscribeOn(scheduler)

      
Cambia el hilo en el que viaja la suscripción hacia arriba y, por lo tanto, el hilo en el que la fuente empieza a emitir. Su posición en la cadena casi no importa. Si hay varios en la misma cadena, gana el más cercano a la fuente (el primero en el código); los demás no cambian el hilo de la fuente.

    

    

      
publishOn(scheduler)

      
Cambia el hilo de todo lo que está debajo de él. Internamente es una cola: el hilo de arriba encola y un trabajador del scheduler entrega aguas abajo, en el mismo orden. Su posición sí importa, y puede haber varios en la cadena.

El pipeline del repositorio es Flux.range(1, 10).filter(impar).map(...).flatMap(item -> Mono.just(item).subscribeOn(Schedulers.parallel())).doOnNext(...).subscribeOn(Schedulers.boundedElastic()). Al instrumentarlo con el nombre del hilo se observó:

  
    
    
  • range, filter y map corrieron en boundedElastic: el subscribeOn exterior decide dónde arranca la fuente.
    • 
    
  • doOnNext y el suscriptor corrieron en hilos parallel-N en casi todos los elementos (en una medición, solo 24 de 2 500 se entregaron en boundedElastic): cuando el hilo exterior está dentro del ciclo de drenaje (drain loop) de flatMap, entrega él mismo un valor que ya llegó.
    • 
    
  • El orden de salida no se preservó en entre el 21 % y el 33 % de 500 ejecuciones, según la medición (por ejemplo 5, 7, 9, 1, 3). Con concatMap o flatMapSequential no hubo ninguna ejecución fuera de orden.
    • 
    
  • El subscribeOn(parallel()) dentro de flatMap no compite con el subscribeOn(boundedElastic()) exterior: aplica a cada Mono interno, que es otra suscripción distinta.
    • 
  

  
Para observar el hilo hay que pedirlo explícitamente, como hacen los ejemplos del repositorio:

4. Backpressure

  
Backpressure (contrapresión) es el mecanismo con el que el consumidor indica cuánto puede recibir, mediante request(n). Este laboratorio sigue la Estación 1 de la prueba guía: productor rápido, consumidor lento.

Reactor

    

    
Modelo: el productor emite hasta 40 elementos por tick y el consumidor procesa 1 cada 2 ticks. La cola de observeOn de RxJava pide 128 (prefetch) y repone de a 96 (75 %). En Reactor, publishOn usa prefetch 256 y repone de a 192, así que los números cambian. La memoria es una estimación (≈ 16 B por Integer, ≈ 1 KB por byte[1024]).

  


  

    Datos medidos en la preparación de la Estación 1.
    
    
      
  • Observable + observeOn con consumidor Thread.sleep(1): con 10 000 elementos, el productor terminó en ~174 ms con ~9 998 lecturas todavía pendientes, sin ninguna excepción: la cola de Observable no tiene límite.
    • 
      
  • Con elementos Integer el heap casi no cambia. El problema se hace visible con cargas más pesadas: 20 000 elementos de 1 KB llevaron el heap de 21 MB a 50 MB.
    • 
      
  • Flowable + observeOn sin ningún onBackpressureX ya aplica backpressure: nunca hubo más de 128 elementos pendientes.
    • 
      
  • onBackpressureDrop sobre Flowable.range(1, 5000) descartó 4 872 de 5 000 elementos (5 000 − 128): range emite todo antes de que el consumidor pida más.
    •

    Pregunta para discutir (Estación 1). ¿Qué estrategia elegiría para las lecturas de temperatura de una planta industrial, y cuál para los «me gusta» de una red social? Tenga en cuenta que una lectura perdida puede ocultar el cruce de un umbral de seguridad, mientras que un «me gusta» intermedio no cambia el contador final. Considere también que un sensor físico es una fuente hot: no se le puede pedir que espere, así que request(n) por sí solo no lo frena. ¿Qué cambia si el sensor envía un promedio por segundo en lugar de cada lectura?
  







  
5. Hot y Cold publishers

  
Un publisher cold ejecuta la secuencia completa para cada suscriptor. Un publisher hot emite una sola vez y los suscriptores reciben lo que se emite desde que llegan.


  

    

      Dos paneles de monitoreo que se suscriben en momentos distintos
      

        
        
        
        
      

    

    

      
      
      
    

    

      
      
    

    

    

    

    

  


  

    autoConnect(2) puede parecer Cold. La Estación 4 sugiere .publish().autoConnect(2). Con ese operador la fuente no empieza a emitir hasta que llega el segundo suscriptor, así que ambos paneles reciben 0..4 y el resultado se ve igual que con un Flux cold. Para observar el comportamiento hot hay que conectar antes de que llegue el panel tardío: autoConnect(1) o ConnectableFlux.connect(). Verificado: con connect() y el panel B llegando a los 2,5 s, B recibió solo 2, 3 y 4.
  

  
En Reactor, share() equivale a publish().refCount(): conecta con el primer suscriptor y se desconecta cuando no queda ninguno. replay(n) guarda los últimos n elementos para entregarlos a los suscriptores tardíos.







  
6. Manejo de errores y resiliencia

  
En un flujo reactivo un error es una señal terminal. Los operadores de resiliencia lo interceptan para reintentar, limitar el tiempo o reemplazarlo por un valor de respaldo. El orden de esos operadores cambia el resultado.

      intento fallido
      cortado por timeout
      espera de backoff

El servicio del repositorio falla ~10 % de las veces. Las respuestas lentas se agregan en el laboratorio para poder observar timeout. Backoff según Retry.backoff(3, 100 ms): esperas de ≈ 100, 200 y 400 ms con jitter de ±50 % por defecto.

  


  

    El orden de los operadores importa.
    
    
      
  • onErrorResume antes de retryWhen: el error se convierte en el valor de respaldo antes de llegar a retryWhen, así que nunca se reintenta (intentos = 1).
    • 
      
  • Cuando se agotan los reintentos, lo que llega a onErrorResume no es la excepción original sino una RetryExhaustedException («Retries exhausted: 3/3») con la original como causa. Se detecta con Exceptions.isRetryExhausted(e); para propagar la original se usa .onRetryExhaustedThrow((spec, signal) -> signal.failure()).
    • 
      
  • timeout antes de retryWhen limita cada intento. timeout después de retryWhen es un presupuesto total para todos los intentos y esperas; al vencer llega una TimeoutException.
    • 
    

  


  

    

      
retry(n) y retryWhen(Retry.backoff(...))

      
retry(3) se vuelve a suscribir de inmediato. Si el servicio falla por sobrecarga, los reintentos inmediatos aumentan la carga justo cuando el servicio está peor. Retry.backoff espera tiempos crecientes, y el jitter evita que muchos clientes reintenten al mismo tiempo.


Retry.backoff(3, Duration.ofMillis(100))
     .maxBackoff(Duration.ofSeconds(2))
     .filter(e -> e instanceof IOException)   // solo errores transitorios
     .onRetryExhaustedThrow((spec, s) -> s.failure());

    

    

      
Reintentar exige una fuente perezosa

      
Reintentar consiste en volver a suscribirse. Si la llamada ya se ejecutó al construir el Mono, la nueva suscripción no la repite.


// Mal: llamar() se ejecuta una sola vez, al ensamblar
Mono.just(⟦servicio.llamar()⟧).retry(3);

// Bien: cada suscripción vuelve a invocar el servicio
Mono.fromCallable(() -> servicio.llamar()).retry(3);
Mono.defer(() -> servicio.llamarAsync()).retry(3);

    

  


  

    Caso en que reintentar automáticamente es peligroso. Un POST /pagos que cobra $350.000 a una tarjeta. La pasarela procesa el cobro, pero la respuesta tarda más que el timeout de 2 s. El cliente recibe TimeoutException, retryWhen repite el POST y el cliente queda cobrado dos veces. La operación no es idempotente. Opciones: no reintentar errores posteriores al envío, enviar una clave de idempotencia para que el servidor descarte duplicados, o reintentar solo cuando la petición no salió (fallo de conexión).

webClient.post().uri("/pagos")
    .header("Idempotency-Key", pedido.getId())      // el servidor deduplica
    .bodyValue(cobro)
    .retrieve()
    .bodyToMono(Recibo.class)
    .retryWhen(Retry.backoff(2, Duration.ofMillis(200))
                    .filter(e -> e.getCause() instanceof ConnectException));

  







  
7. Pruebas con StepVerifier

  
StepVerifier (módulo reactor-test) se suscribe al publisher y verifica señal por señal: cada onNext, su orden y la señal terminal. Con tiempo virtual, un flujo que espera segundos se prueba en milisegundos.

  

    

      
Secuencia exacta


@Test
public void secuenciaExacta() {
    Flux<String> pipeline = Flux.range(1, 10)
        .filter(i -> i % 2 == 1)
        .map(i -> "Number: " + i);

    StepVerifier.create(pipeline)
        .expectNext("Number: 1", "Number: 3", "Number: 5")
        .expectNext("Number: 7", "Number: 9")
        .verifyComplete();
}

    

    

      
Tiempo virtual


@Test
public void tiempoVirtual() {
    StepVerifier.withVirtualTime(() -> Flux.just("a", "b", "c")
                .delayElements(Duration.ofSeconds(5)))   // creado DENTRO del Supplier
        .expectSubscription()
        .expectNoEvent(Duration.ofSeconds(5))
        .expectNext("a")
        .thenAwait(Duration.ofSeconds(5))
        .expectNext("b")
        .thenAwait(Duration.ofSeconds(5))
        .expectNext("c")
        .verifyComplete();   // 15 s virtuales, milisegundos reales
}

    

  

  
El Flux debe crearse dentro del Supplier. withVirtualTime reemplaza los schedulers de tiempo por un VirtualTimeScheduler antes de invocar el Supplier; si el Flux se creó antes, delayElements ya quedó atado al reloj real. expectSubscription() va antes de expectNoEvent porque la suscripción también cuenta como evento.


  

    

      Reloj virtual y reloj real
      

        
        
      

    

    

    

      

      
    
    
    
    
    
  
    

  
    
    Pruebas intermitentes con flatMap. Si el pipeline usa flatMap con publishers internos asíncronos, un expectNext(1, 3, 5, 7, 9) estricto falla en algunas ejecuciones, porque el orden depende de qué interno termina primero (sección 3). Para estos casos hay dos opciones: usar concatMap o flatMapSequential si el orden es un requisito, o verificar el contenido sin orden.

    StepVerifier.create(flujoConFlatMapAsincrono)
    .recordWith(ArrayList::new)
    .expectNextCount(5)
    .consumeRecordedWith(xs -> assertEquals(
        new HashSet<>(Arrays.asList(1, 3, 5, 7, 9)), new HashSet<>(xs)))
    .verifyComplete();
    
  
    
  
    StepVerifier verifica cosas que un assertEquals sobre una lista no puede: el orden de llegada, que el flujo complete (o falle con el error esperado), que no haya señales de más y el comportamiento en el tiempo. No verifica en qué hilo se ejecutó cada etapa ni el comportamiento con carga real.
    

    



    
  
    8. WebFlux y Server-Sent Events
    
  
    En Spring WebFlux un controlador puede devolver Mono o Flux. El framework se suscribe y escribe cada elemento en la respuesta HTTP sobre Netty, sin dedicar un hilo por petición.
    

    @RestController
@RequestMapping("/reactive")
public class ReactiveController {

    @GetMapping("/mono")
    public Mono<String> getMono() { return Mono.just("Hello, Mono!"); }    // 1 valor

    @GetMapping("/flux")
    public Flux<String> getFlux() { return Flux.just("Hello, Flux!"); }    // 0..N valores

    @GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<String> getStream() {
        return Flux.interval(Duration.ofSeconds(1))     // 0, 1, 2, ... cada segundo
                   .filter(i -> i % 2 == 0)
                   .map(i -> "evento " + i)
                   .doOnCancel(() -> log.info("cliente desconectado"));
    }
}

    Con produces = TEXT_EVENT_STREAM_VALUE

    Simulación con un tick cada 0,8 s. El laboratorio se desconecta solo después de 12 ticks; un Flux.interval real no termina nunca.
    
  
    

  
    
    Diferencia real entre los dos endpoints. Un Flux<String> sin produces también llega por partes: se envía como text/plain con codificación por bloques (chunked), pero sin delimitadores, así que el cliente recibe «evento 0evento 2evento 4» pegado. Ambos endpoints hacen streaming; lo que cambia con SSE es el protocolo. SSE envía eventos delimitados (líneas data: seguidas de una línea en blanco, con campos opcionales id y event), que el navegador consume con EventSource y que permiten reconexión automática con Last-Event-ID. Para enviar esos campos desde Spring se devuelve Flux<ServerSentEvent<T>>.

    // Navegador
const es = new EventSource("/reactive/stream");
es.onmessage = e => console.log(e.data);   // "evento 0", "evento 2", ...
    
  
    
  
    Cuando el cliente cierra la conexión, WebFlux cancela la suscripción y Flux.interval deja de emitir (doOnCancel lo registra). Devolver un Flux no garantiza que el endpoint sea no bloqueante: si dentro del pipeline hay una llamada JDBC, ese hilo de Netty queda bloqueado.
    

    



    
  
    9. Cuándo usar programación reactiva
    
  
    La programación reactiva tiene costos concretos. Conviene usarla donde sus ventajas compensan esos costos.
    
  
    
    
    
      
    Cuándo conviene
    
      
      
        
    • Flujos continuos de datos: SSE, WebSockets, telemetría, consumo de Kafka.
      • 
        
    • Muchas conexiones concurrentes dominadas por E/S, con todo el stack no bloqueante: WebClient, R2DBC, drivers reactivos de MongoDB, Redis o Cassandra.
      • 
        
    • Composición de llamadas asíncronas: combinar tres servicios con zip, aplicar timeouts y reintentos por llamada.
      • 
        
    • Necesidad de backpressure de extremo a extremo entre productor y consumidor.
      • 
      
    
    
    
    
    
      
    Cuándo no conviene
    
      
      
        
    • Acceso a datos bloqueante. JDBC y JPA bloquean el hilo y rompen el modelo. Envolverlos con subscribeOn(Schedulers.boundedElastic()) solo mitiga el problema: el hilo sigue bloqueado, aunque sea uno del pool elástico.
      • 
        
    • Depuración. Las trazas de error muestran internos de los operadores y no la línea que ensambló el pipeline. Existen ayudas (checkpoint("..."), Hooks.onOperatorDebug(), ReactorDebugAgent de reactor-tools), con costo de rendimiento en algunos casos.
      • 
        
    • Curva de aprendizaje. Hilos, orden, hot/cold y backpressure son fuente de errores sutiles para un equipo sin experiencia.
      • 
        
    • Propagación. Cuando un método devuelve Mono, quienes lo llaman también tienden a volverse reactivos.
      • 
        
    • Trabajo intensivo en CPU. No hay ganancia frente a un pool de hilos.
      • 
      
    
    
    
  
    

  
    Alternativa: hilos virtuales (Java 21)
    
  
    Los hilos virtuales (JEP 444) hacen barato bloquear: el hilo virtual se desmonta del hilo de plataforma mientras espera E/S. Para muchos servicios dominados por E/S, esto da la escalabilidad del modelo no bloqueante con código imperativo, trazas de error legibles y drivers JDBC normales. En Java 21 un bloque synchronized fija (pin) el hilo de plataforma; Java 24 corrige esa limitación (JEP 491).
    
  
    

    // Estilo bloqueante, un hilo virtual por tarea
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<Pedido> f = executor.submit(() -> repositorio.buscar(id));
}
// Spring Boot 3.2+: spring.threads.virtual.enabled=true
