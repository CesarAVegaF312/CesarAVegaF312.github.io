Integración Continua (CI)

Práctica de integrar los cambios de código con frecuencia y verificar cada integración de forma automática con un build y pruebas. En este material se trabaja con GitHub Actions sobre el proyecto del taller.

1. ¿Por qué integrar con frecuencia?

Ejemplo: tres desarrolladores trabajan en paralelo durante dos semanas. Lo que cambia es cada cuánto integran su trabajo.

¿Cada cuánto integra el equipo?
14integraciones en 14 días
14esfuerzo total de integración (unidades relativas)
0 díastarda en descubrirse el defecto que Luis introdujo el día 2

Modelo ilustrativo, no una medición: si cada persona cambia algo cada día, al integrar después de n días cada cambio puede chocar con los n cambios de los demás, así que el esfuerzo de cada integración crece aproximadamente con n².

Conclusión. El esfuerzo de integrar crece más rápido que el tiempo que se pasa sin integrar. Por eso conviene integrar cambios pequeños con frecuencia.

Prácticas de CI

Integrar a diario

Cada persona integra su trabajo a la rama principal al menos una vez al día. Las ramas que duran semanas generan el mismo problema de la integración tardía.

Build automático y autoverificable

Un solo comando compila y ejecuta todas las pruebas, y el resultado (éxito o fallo) no requiere interpretación manual.

Corregir el build roto de inmediato

Cuando el pipeline queda en rojo, el equipo lo corrige antes de integrar nuevos cambios.

    Pasos con if: always()
    Por defecto, cuando un paso falla GitHub omite los siguientes. Con if: always() el resumen y los reportes se ejecutan de todas formas, porque son los que permiten entender el fallo. Observe además que cuando falla la compilación no hay nada que publicar, mientras que cuando fallan las pruebas sí quedan los reportes de Surefire.
    
    
    Umbral de cobertura en el pom.xml
    El pipeline solo ejecuta mvn verify. La regla del 80% vive en el plugin de JaCoCo, así que el mismo comando da el mismo resultado en el portátil de cualquier integrante y en el servidor. Si el pipeline ejecuta pasos que no se pueden reproducir en local, los fallos son más difíciles de depurar.

    Limitación de la cobertura. JaCoCo mide qué líneas se ejecutaron durante las pruebas, pero no si las pruebas verifican el resultado. Una prueba sin aserciones aumenta la cobertura sin detectar errores. El umbral del 80% ayuda, pero no reemplaza la revisión de código.

    5. Versiones de las actions
    
  
    Las actions se ejecutan sobre un runtime de Node.js. Cuando GitHub retira una versión de Node.js, los workflows que usan versiones antiguas de las actions dejan de estar soportados.
    
  
    
    
    
      ¿Qué pasa hoy con actions/checkout…?
      
    
        
        
        
      
    
    
    
    
    
    Hitos (○): 14 ago 2023, Node 12 retirado · 3 jun 2024, se fuerza Node 20 sobre node16 · 16 jun 2026, Node 24 por defecto · 23 sep 2026, Node 20 retirado.
    
    
    
  
    
  
    
    Recomendaciones. actionlint marca @v2 como obsoleta, pero no @v4, así que el linter no basta para saber si una versión sigue vigente. Antes de copiar un workflow de un tutorial, revise la página de releases de cada action.
  
    
  
    Fuentes: GitHub Changelog, retiro de Node 12 (2023-07-17), Node 16 → Node 20 (2024-03-06), deprecación de Node 20 (2025-09-19) y retiro de Node 20 (2026-09-23).

    ConceptoGitHub ActionsGitLab CIJenkins
    
    
      
    Dónde se define.github/workflows/*.yml.gitlab-ci.yml en la raízJenkinsfile (pipeline declarativo)

    Unidad de trabajojob → stepsstage → jobs → scriptstage → steps
    
      
    Reutilizaciónactions (uses:)include:, templates, componentsplugins, shared libraries
    
      
    Evidenciasupload-artifact, step summaryartifacts:, reports: junitarchiveArtifacts, junit
    
        
  
    
  
    
  
    
    Detalles a tener en cuenta. En GitLab, si el job no declara image:, en los runners compartidos de GitLab.com corre sobre una imagen de Ruby sin Java ni Maven. En Jenkins, la terminología actual es controller y agent; «master/slave» es la nomenclatura antigua que aún aparece en documentación vieja.
